- `src/lib/fixtures/{users,receivables,claims,flags,auditLog}.ts` — the exact roster from the phase doc §3 (Karnaphuli/Nordicwear flagship scenario, the three Padma/Jamuna/Meghna claims with correct approve/reject math, the Turag Apparel linked-entity flag with the pre-calculated BDT 160 fee, and the `Anchor #128` Merkle entry).

- `src/components/{receivable,claim,flag,audit}/*` — the reusable components named in the phase doc §5 (`ReceivableTable`, `ReceivableStatusBadge`/`StatusBadge`, `SubmitReceivableForm`, `AttestationCard`, `ClaimTable`, `CapacityMeter`, `SubmitClaimForm`, `FlagReviewCard`, `ClearFlagDialog`, `AuditLogList`, `AnchorEventCard`).

## Deviations from the phase doc (logged per `CLAUDE.md` §6.2)

- **Tailwind v4, not v3.** `create-next-app@latest` now scaffolds Tailwind v4, which configures via CSS `@theme` blocks in `globals.css` instead of `tailwind.config.ts` (no such file exists in v4). The brand palette (`navy-950/900`, `teal-900/700`, `emerald-500`, `amber-600`, `brick-500`) is wired as `--color-finclaim-*` tokens there — same effect the phase doc asked for (named theme colors, no hardcoded hexes in components), different mechanism.
- **shadcn CLI is on a newer major version** than the phase doc's commands assumed (prompts for a `radix`/`base`/`aria` primitive library and a style preset). Used `-b radix -p nova`; the generated primitives are the same shadcn/ui components (`button`, `card`, `table`, `badge`, `dialog`, `input`, `label`, `tabs`, `textarea`, `avatar`, `separator`, `sonner`, plus `select`, `dropdown-menu`, `sheet`, `skeleton` for the shell/forms/dialogs). The `checkbox` component (needed for the flag-clearing two-step) is hand-written in the same style — `ui.shadcn.com` was unreachable for that one `add` call in this sandbox, but the underlying `radix-ui` package was already installed, so it's a straight port of the standard shadcn checkbox.
- **No `next/font/google`.** Turbopack's font loader couldn't resolve `fonts.gstatic.com` in this sandbox and failed the build. Switched to a native system-sans stack in `globals.css`'s `--font-sans`, which the phase doc §2 already allowed ("a clean system/sans stack (e.g. Inter, already shadcn's default)").
- **State management uses `useSyncExternalStore`, not `useState`+`useEffect`.** The naive "hydrate from `localStorage` in a `useEffect`" pattern is flagged as an error by the `react-hooks/set-state-in-effect` ESLint rule bundled with this Next.js version, and — more importantly — it caused a real bug: hard-reloading a nested protected route (e.g. `/regulator/flags`) briefly saw a null session before the effect corrected it, bounced through `/login`, and landed on the role's *root* dashboard instead of staying put. Fixed by making the session's "not yet resolved" state (`undefined`) explicitly distinct from "logged out" (`null`) in `session-store.ts`, and gating `RoleGuard`/`/login`/`/`'s redirect effects on that. Verified fixed with a headless-browser hard-navigation test.
- **Extra plumbing beyond the phase doc's exact file list**: `lib/{session-context,session-store,data-context,app-data-store,capacity,ids}.ts` and `hooks/useAppData.ts`. The phase doc's folder sketch only named `hooks/useSession.ts`, but the live submit→attest / submit-claim / clear-flag / freeze flows need shared mutable state beyond the read-only session — this is that layer, kept in `lib/` as plain modules with a thin React binding, not embedded in components.
- **"Reset demo data" control removed from the UI** (3 Sept, post-Phase-1 session, direct user instruction) — it was in the AppShell topbar menu next to Sign out, and its label read as exactly the kind of demo-mode disclosure `CLAUDE.md` §3 forbids. The underlying capability (`resetToFixtures` in `lib/app-data-store.ts`, exposed through `AppDataProvider`/`useAppData`) is left in place — nothing calls it from the UI anymore, but it's still there if the team wants to wire it back in behind something judges won't see (e.g. a keyboard shortcut) before presenting.
- **Buyer contact name invented**: the phase doc names Nordicwear Sourcing ApS as the buyer institution and gives its login email, but no contact person. Added "Mette Johansen, Trade Finance Officer" (a realistic Danish name, matching a Copenhagen company) for the person-level display next to the institution — not one of the "don't invent" Bangladeshi roster entries, so this doesn't conflict with `CLAUDE.md` §3's no-placeholder-names rule.
- Removed the default `create-next-app` placeholder SVGs from `public/` (unused).
- **Login page now has a "Quick access" panel** (`src/app/login/page.tsx`) listing all six identities by role/institution/name for one-click sign-in — added per direct user instruction (3 Sept, post-Phase-1 session) for faster access when presenting. This is a deliberate, explicit change to the phase doc §3 instruction to "never render this list in the UI as a hint list": the panel shows role, institution, and name (needed for the "jump straight into a workspace" affordance the user asked for) but still never prints an email address, and a typed-in unmatched email still falls back to a generic "Invalid email or password" error rather than hinting at valid ones — so the original anti-hint concern (an on-stage mistyped password shouldn't reveal which emails are valid) is preserved. Labeled "Quick access," not "demo credentials" — the non-negotiable no-mock/demo-labeling rule (`CLAUDE.md` §3) stays intact.
- **Login and homepage backgrounds are white**, not the navy-950 the login page originally used — per direct user instruction (3 Sept) to keep all site pages, including login, on a clean white background. `AppShell`'s dashboard wrapper was also switched from `bg-muted/30` to `bg-white` for the same "clean" look. Brand navy/teal remain as accents (buttons, icons, the sidebar, status badges) — only full-page backgrounds changed.
- **Fixed a pre-existing logo-distortion bug** while building the homepage/login header: `logo_v2.png` is a wide icon+wordmark+tagline lockup (~3:1 aspect ratio), but the Phase 1 code requested it at forced-square dimensions (e.g. `width={56} height={56}`), squashing it into an illegible dark blob — not very visible against the old navy-950 login background, but glaring against the new white one. Fixed on the marketing/login surfaces by sizing the image at its true aspect ratio and dropping the redundant hand-typed "FinClaim" text next to it (the lockup image already contains the wordmark).
- **Sidebar background is now white** (3 Sept, post-Phase-1 session, direct user instruction). `Sidebar.tsx` previously filled with dark navy (`--sidebar: var(--finclaim-navy-900)`). Now: the `--sidebar-*` tokens in `globals.css` resolve to the same white/light palette as the rest of the app (`--sidebar: white`, `--sidebar-accent`/`--sidebar-accent-foreground` reuse the existing light-teal `--accent` tokens, `--sidebar-border` reuses `--border`) so `Sidebar.tsx`'s existing `bg-sidebar`/`text-sidebar-foreground`/active-nav classes needed no changes beyond the token values, and the sidebar now matches the rest of the "white and clean" site. **`.dark` mode's sidebar tokens were left untouched** — dark mode isn't wired up anywhere in the app (no `ThemeProvider`), so this was out of scope; if dark mode is ever wired up, give its `--sidebar-*` block the same light-sidebar-on-dark-app treatment or explicitly decide the sidebar should stay dark there.
- **Sidebar logo swapped off the distorted 32x32 crop of `finclaim-logo.png`** — was being requested at forced-square dimensions against a ~3:1 source image (the same bug described above), just less visible on the old dark sidebar. The team was actively iterating on the replacement asset/size in `Sidebar.tsx` live in the editor as of this session's last edit (landed on `public/brand/logo_v2.png`, a newer wide icon+wordmark+tagline lockup someone added to `public/brand/` mid-session) — **whoever picks this back up should sanity-check the `width`/`height` on that `<Image>` against the asset's real aspect ratio** (check via the PNG's own header, e.g. `logo_v2.png` is 1942x809 ≈ 2.4:1) before calling it done, since a mismatched width/height reintroduces the exact squash bug this note is about.
- **All em dashes removed from `frontend/src`** (3 Sept, post-Phase-1 session, direct user instruction) — 41 occurrences across 18 files (fixture descriptions, toast messages, UI copy, the marketing homepage, and a few code comments) replaced with a plain hyphen. Re-check any new copy added after this date; nothing enforces this automatically (no lint rule), so it depends on whoever writes the next batch of text noticing the convention.
